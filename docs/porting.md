# 実験スクリプトからの移植（2026-11-04）

実験用リポジトリ（非公開）の `tools/s4-boot.py`（15,289 行・版 `279d7df58625`）から、Mirakurun 用の起動
（`tools/dth50-mirakurun.sh` → `tools/run-ch27-vendor.sh` の旗）で**実際に通った文だけ**を移した。
通った文は、開発機を再起動して cold・warm で 1 回ずつ走らせ、行単位で記録した（実験用リポジトリ（非公開）の `docs/10-porting-map.md`）。

## そのまま残したもの（実験時代の旗）

効いているか分からないものも含めて、本筋で通った書き込みはそのまま（`stream.Options` の既定値）:
三つ組 3 回（2 回目以降は +0x7c = 0x100・+0x5c = 0x1000）・三つ組と閉じる前の 0x0d・[文脈+0x3c] の bit14 落とし・0x15・
[文脈+0x4c] |= 0x04000000（流れの文脈と、表 1/表 2 の全文脈）・[枠+0x628/+0x618/+0x5d8/+0x5d0] = 1・[文脈+0x31c] の補い・
定常 0x0b の 2 回目以降 +0x1bc = 0・IOVA 0 の頁・副1 のバッファ 256 本・0x15 の前の枠 6 の印の書き込み。
実機で動くことを確かめてから、1 つずつ外して要るかを確かめる。

## 移さなかったもの

- **計器**（読んで表示するだけ）: `*_dump`・`*_probe`・`ecm_timeline`・`ledger_seats`・`cdxm_gates_dump`・`fw_vars_dump` など
- **索引を書いて元に戻すだけの計器**: `pidfilter_dump`（0x6040）・`seat_map`（0x6040 / 0x6080）・`scan_6084`（0x6080）
- **通っていなかった旗**（記録で確かめた）:
  - `--sub1-c60-or 0x100`: `ts_cmd8` の中で `SUB1_C60_CLEAR` の枝の内側に字下げされていて、本筋では一度も効いていない
  - `--secured-pids` / `--secured-const`: `ts_grab` の中の代入が局所変数になっていて、`ts_cmd8_sub5` には届いていない

⚠️ 計器を外したので、コマンドの間の時間は実験より短い。時間に依存する所があれば実機で出る。

## 振る舞いの違い（意図したもの）

- ホストのバッファの 0xA5 埋めは 1 バイトずつではなく一度に書く（カードへのコマンドより前・結果は同じ）
- 定常運転の止め方: 実験の「新規 0 の周回が 2 回 or 無データ 2 秒」は、周回ごとに数が 0 に戻るので実際は「無データ 2 秒」だけ。移植はそれをそのまま書いた
- ロックしなければ止める（実験の `--force` は無い）。0x19 を出す前に止まった回は閉じる手順を出さない（実験と同じ）
- 汲み出しは合流した 1 本（exit → dec）だけを書く。環ごとのファイルは書かない（実験の `--exit-pump-no-files`）
- 副1 の TS（定常運転の間）は捨てる（実験は `/tmp/…-ch27.ts` に書いていた）

## 確かめたこと（模擬・2026-11-04）

実験の関数と移植を、同じ「記録する偽のカード」（BAR0 の窓越しのメモリと BAR2 のレジスタ）に対して走らせ、
カードへの書き込み列を比べた（窓レジスタ 0x43C の書き込みは読み返しの回数で増減するので除く）:

- 部品ごと: 0x09・0x0d・0x1a・0x19・0x0b（初回・定常）・0x08 副1・副5（下ごしらえ・三つ組・PMT 前）・0x15・SECODE（塊も一致）・
  +0x628 など・+0x31c・+0x4c・PID 表 128 段・I2C（波形確認・初期化列・ch27 の選局・ロックの読み）・閉じる・手順書の読み → **全部一致**
- 通し: 実験の `main --warm --close-xp --ts-grab …`（本筋の旗）と、移植の `boot.warm` → `Stream.open/steady/pump/close` を、
  コマンドに完了を返す偽のファームに対して → コマンドの並び `d 9 9 1a 1b 19 b b 8 8 15 b d 9 [9 8] 8 15 b d 9 8 15 b … d 9 9 1a` と
  **6,534 書き込みが一致**（計器の索引レジスタ 0x6040 / 0x6080 を除く）

## 実機で分かったこと（2026-11-04）

- **三つ組の 0x09 の前は、[文脈+0x3c] bit14 が立つのを待ってから落とす。** ファームは SECODE の後しばらくして bit14（停止の印）を立てる。
  計器を外した移植は間を空けずに落としに行き、まだ 0 で何も落とせず、その後に立った印で 0x09 副5 が 8 秒返らなかった
  （三つ組を打ち切り、dec の環ができず、映像・音声はスクランブルのまま exit の環に残った）。`--settle 0.5` で間を空けると
  0x4000 → 0 と落とせて 0x09 は 8 ms で返り、映像 0x100・音声 0x110 が平文 100%（dec 13.4 Mbps）になった。
  実験では計器の読み出しがこの待ちになっていた。移植は bit14 が立つのを最大 2 秒見張ってから落とす（`Options.stop_flag_wait`）。
- **SECODE の後は、非同期の 2 段が終わるのを待つ。** SECODE は返った後もファームの中で 2 段の処理が続く（実験の `secode_report`）。
  最後の SECODE の後すぐに文脈の欄の補いと定常運転へ進むと、三つ組は通っても dec の環に何も出ず、exit の環に PID の揃わない
  データが出た。0.5 秒空ける（`--settle-final 0.5`）と復号した。移植は、gp-0x7da4（非同期①の完了）と gp-0x7da0（非同期②の完了）が
  gp-0x7db8（ハンドラに入った回数）に追いつくまで待つ（`Options.secode_async_wait`・実測 9〜11 ms）。
  これで `--settle` なしで復号（映像 0x100・音声 0x110 が平文 100%・dec 14.2 Mbps・開くまで 1.8 秒・warm）。
- 三つ組 2 回目で流れの文脈（[gp-0x6c94] から辿る）が 0 の回があり、そのときは副1 を開き直さない。実験でも起きている
  （08:01 の Mirakurun 経由の ch27）。復号はそれでも通った。

- **cold も確認**（2026-11-04 11:01・再起動の直後・橋を止めて）: 初期化列 1,066 操作・ファーム転送 0.1 秒・転送後の手順 9,312 操作（許容 4 件）・
  窓 1 で 213 語が書き換わる → 選局 → 三つ組（2 回目で副1 を開き直す枝も通った）→ 映像 0x100・音声 0x110 が平文 100%・dec 12.9 Mbps・
  起動から開くまで 3.3 秒・閉じる 4 段とも返った。
- 実験の橋（dth50-bridge）がカードを握っている間に起動すると、vfio-pci の unbind が相手が手放すまで黙って待ち、取り合いになった
  （その回は dec 0 本）。移植は、カードが vfio-pci に付いていてグループが開けない（EBUSY）なら起動しない。

- **PCIEW のチューナー 2**（2026-11-04）: 実験からの移植ではなく、ベンダのフィルタの MJ110 の処理を動かして取った列
  （`tools/extract_mj110.py`・`TunerMJ110`）。`tuner-probe --tuner 2` で ch27・ch13 ともロック。1 つ目は `Tuner`（1 つ目専用）のまま、
  `tuner-probe --tuner 1 -c 27` でロック（253 取引・NAK 1 件 = 不在の 0x3C）。docs/hardware.md「2 つ目のチューナー」。
  `stream --tuner 2` は 0x08 副1 の +0x08 を 1 にするだけで、カード内復号まで通った（dec 約 14 Mbps・2 回とも）。
- **warm の連続で dec 0 の回があった → カードの起動し直しの再試行で直した**（2026-11-04）。
  - 症状: 22 回中 9 回、開いて閉じるまで全部の段が返るのに dec 0 本。exit にスクランブルのままの映像・音声が出る。
    40 秒流しても 0 のまま（遅れではない）。失敗の次は必ず成功し、成功の次はたいてい失敗した。チューナー（1・2）とは無関係。
  - 外れた筋: 復号器の席（銀行 A は毎回返されている）・閉じた後に残る濾過器の arm（0x6084 を 0 にしても失敗は残った）・
    ECM の周期や版の偶奇（ECM は約 2.1 秒ごとに変わる）・閉じてから開くまでの間（どの回も約 0.18 秒）。
  - 原因: 最初の定常 0x0b（+0x1bc = 1）でファームが B-CAS カードを起動し直した後、失敗する回はリセット応答（ATR）が
    届かない。カードの通信の表 0xa02309f8 の +0x118 bit1（準備完了）が立たず、ATR の解析結果（+0x124/+0x128/+0x12c）は 0、
    ATR 受信の計数器（0xa0101f00 帯 +0x8/+0xc）も増えない。ECM タスクは準備完了を待ったまま ECM を 1 つも受けない。
    なぜ応答が来ないかは未解明。
  - 直し（`Stream.steady`）: 周回ごとに準備完了を読み、起動し直してから 0.8 秒立たなければ次の 0x0b を +0x1bc = 1 にして
    もう一度起動し直す（最大 3 回・立つまで定常運転を最大 3 秒延ばす）。実機で 7 回連続（1 つ目 6・2 つ目 1）すべて復号し、
    うち 2 回で起動し直しが 1 回入った（2 回目は 0.42 秒で準備完了）。

まだ確かめていないこと: 実験時代の旗を外して要るかどうか・起動し直しても ATR が来ない回がなぜあるか・DT-H50/PCIE・橋とクライアントの移植版への切り替え。
