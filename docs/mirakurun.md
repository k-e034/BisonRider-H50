# Mirakurun で使う

Mirakurun から見たチューナーは「チャンネル番号を受け取り、その物理チャンネルの TS を標準出力へ出し続けるコマンド」。
このドライバの `stream` がそれにあたる。B-CAS の復号はカードの中で済んでいるので、Mirakurun の `decoder` は書かない。

Mirakurun は公式の推奨どおり Docker（`chinachu/mirakurun`）で動かす。コンテナの中からはカード（root・VFIO）を扱えないので、
ホストの橋とコンテナの中の薄いクライアントに分ける。

```
Mirakurun（コンテナ）── spawn ── node /dth50/dth50-client.js <ch> <tuner>
                                     │ Unix ソケット（ホストの /run/dth50/tuner.sock）
ホスト: python3 -m dth50 bridge（root・systemd・カードを握り続け、2 チューナーを同時に流す）
```

| ファイル | 役目 |
|---|---|
| `dth50/bridge.py` | 「チャンネル番号 [チューナー番号] + 改行」を受けて開き、TS をソケットへ流す。接続が切れたらその流れだけを閉じる。カードを 1 回だけ開いて握り続け、2 つのチューナーを同じプロセスで同時に扱う（下の「同時受信」）。同じチューナーへの次の要求は、前の回が閉じ終わるまで最大 30 秒待たせる。`--spawn` で以前の動き（要求ごとに `stream` を起動・1 本ずつ） |
| `contrib/mirakurun/dth50-client.js` | コンテナの中のクライアント（Node の標準機能だけ）。SIGTERM ですぐ切る |
| `contrib/mirakurun/docker-compose.override.yml` | 公式の `docker-compose.yml` に重ねる（`/run/dth50` とクライアントを `/dth50` の下に渡す）。公式のファイルは書き換えない |
| `contrib/mirakurun/tuners.yml` | チューナーの設定（2 つ。クライアントの 2 つ目の引数がチューナーの番号） |
| `contrib/systemd/dth50-bridge.service` | 橋の systemd ユニット（`contrib/install.sh` がリポジトリとベンダのデータの場所を埋める） |

## 同時受信

> 2026-11-11 に、2 本同時に開く途中でカードが固まる失敗があった（4 つの原因を 2026-11-17 に直した。
> [hardware.md](hardware.md) の「2 本同時で起きた致命的な失敗と直し方」）。

DT-H50/PCIEW の 2 つのチューナーを同時に使える。カード内の復号の仕組み（SECODE）は 1 つしか載らず、2 回出すとカードが止まる
ので、2 本目は SECODE を出さず、副5 を正しくつないで開くだけにする（[hardware.md](hardware.md) の「2 つを同時に使う」・
「2 本目の復号が壊れていた」）。⚠️ 2026-11-18 までは 1 本目の欄を写していて、2 本目が流れ始めてからの最初の鍵の切り替わりで
2 本とも映像が壊れていた（暗号の印は 0 のままなので、印だけの確かめでは分からなかった）。

- 流れが無いときに開く回が 1 本目（SECODE・カード全体の手順）。もう 1 本が流れている最中に開く回は空いている席で開く。
  どちらを先に閉じてもよい。最後に閉じる 1 本だけがカード全体を止める（0x1a）。
- 開く・閉じるは 1 回ずつ通すので、他方を開いている数秒の間、こちらの閉じる・開くは待たされる（流れている方は止まらない）。
- **2 本同時の復号が崩れた状態を見張る**（2026-11-18）: PCIEW の 2 本同時の復号がまれに崩れ、電源を入れ直すまで
  戻らない（[hardware.md](hardware.md) の「2 本同時の復号が崩れる状態」）。橋は開いているカードのファームの数
  0x8021f4e8 を 1 秒ごとに読み（読むだけ）、0 でなくなったら、崩れた時刻と直前の操作をログに出す。崩れたカードでは
  2 本目を開かない（1 本目は開く）。その要求は、空いている別のカードのチューナーを借りて流し、閉じたら返す。
  Mirakurun は断られると別のチューナーへ移らず、同じチューナーを 0.15 秒おきにやり直し続けるので、断るだけでは
  視聴・録画が失敗する（2026-11-18 に確かめた）。借りている間に借りた先のチューナーへ要求が来たら、空くのを
  `--wait-busy` 秒待ってから断る。確かめた: 崩れた PCIEW ＋ PCIE で、Mirakurun から ch27（PCIEW）と ch25（チューナー 2 の
  要求を PCIE で）を同時に流せた。3 本目は断られた。
- 閉じる命令が返らなかったとき・warm で閉じられなかったときは、カードが応答しないとみなし、橋は終わらずに要求をすぐ断る
  （ログに 1 分に 1 回）。PCIe のリセットはチップに届かないので、戻すにはマシンの電源を入れ直す。
- 副5 が文脈を返さなかったときは、ファームが確保したまま返さない区画・鍵の枠を戻し、1.5 秒おいて 1 回だけやり直す。
- どの環も 5 秒進まなければ、その流れを終えて Mirakurun に知らせる。
- **複数のカード**（2026-11-18）: 橋は実機で確かめた機種のカードを全部握り、チューナーにカードをまたいだ通し番号を振る
  （カードを PCI アドレスの順に並べ、カードごとのチューナーを続けて数える）。DT-H50/PCIEW ＋ DT-H50/PCIE なら 3 本、
  PCIEW 2 枚なら 4 本。カードごとに席・区画・鍵の枠・命令の順番を分けて持ち、1 本目（SECODE）とカード全体の手順・
  最後の 0x1a もカードごとに決める。1 枚が応答しなくなっても、他のカードのチューナーは使い続けられる。
  `--bdf` にカンマ区切りで並べれば使うカードを名指しできる。`tuners.yml` にはカードの数だけチューナーを並べる。
  確かめた: PCIEW（04:00.0）＋ PCIE（83:00.0）で ch27・ch25・ch22 の 3 本同時、3 本とも PES の始まり 100%。
- 橋を `--spawn` で動かすときは 1 本ずつしか通らないので、`tuners.yml` の 2 つ目を `isDisabled: true` にする。

## 導入

```bash
# 1) Mirakurun（公式の手順）
sudo mkdir -p /opt/mirakurun && cd /opt/mirakurun
sudo wget https://raw.githubusercontent.com/Chinachu/Mirakurun/refs/heads/master/docker/docker-compose.yml
sudo docker compose pull
sudo docker compose run --rm -e SETUP=true mirakurun

# 2) 橋・クライアント・Mirakurun の設定（ベンダのデータは README の tools/setup_vendor.py で /usr/local/share/dth50 に揃えておく。
#    別の場所なら --vendor DIR）
sudo bash contrib/install.sh install
journalctl -u dth50-bridge -n 3          # 「待ち受け /run/dth50/tuner.sock」

# 3) Mirakurun を作り直して（override を効かせる）チャンネルスキャン（13〜62 を順に・数分）
cd /opt/mirakurun && sudo docker compose up -d
curl -sS -X PUT "http://127.0.0.1:40772/api/config/channels/scan?type=GR"

# 4) 受けてみる（20 秒）
curl -sS --max-time 20 -o ch27.ts http://127.0.0.1:40772/api/channels/GR/27/stream
```

`localhost` は IPv6 の ::1 に向くことがあるので 127.0.0.1 を使う。外すときは `sudo bash contrib/install.sh uninstall`。

## 確かめたこと（2026-11-05・開発機・Mirakurun 4.2.1）

- 橋は起動時に自動で立ち上がり、Mirakurun の番組表の取得（ch13・ch18 …）が `stream` で流れた（番組表 8,880 件）。
- `/api/channels/GR/27/stream` を 20 秒: Mirakurun は番組表の取得を止めて ch27 に切り替え、140,708 パケット・
  188 の境界のずれ 0・映像 0x0100 / 音声 0x0110 とも全部平文。Mirakurun のエラーの計数はすべて 0。
- EPGStation 2.10.0（Docker・Mirakurun に 127.0.0.1:40772 でつなぐ）で時刻指定の予約 2 分 → 199 MB の .m2ts・映像/音声とも全部平文。
- 実験用リポジトリ（非公開）の橋（`tools/dth50-bridge.py` → `dth50-mirakurun.sh` → `run-ch27-vendor.sh` → `s4-boot`）からの置き換え。
  クライアントとソケットのやりとりは同じ（チャンネル番号だけの行も受ける）なので、古いクライアントのままでも動く。

- 同時受信（2026-11-05 08:15〜・Mirakurun に 2 チューナー）: ch27・ch25・ch18 を重ねて受け、ch25 は全部平文・抜け 0、
  ch25 が流れている最中に空いたチューナーで開いた ch18 も全部平文。番組表の取得も 2 チューナーを同時に使う。
  ch27 の頭の 1 秒ほどにスクランブルが残った（下の「頭のスクランブル」）。

## 分かったこと・残っていること（2026-11-05）

- **2 本目の音声が出ず、ライブ視聴が映らない → 直した（2026-11-06）。** NHK 総合の番組の PMT に 2 本目の音声 0x111 が
  載ったとき、出力に 0x111 が 1 本も無く、EPGStation の ffmpeg（`-map 0`）が中身の無い音声で変換器を作れず
  0 フレームで失敗した（`Error initializing filters!`）。0x111 を除けば同じ流れから絵が出た。
  原因: 0x31 の要求に音声を 1 本しか入れていなかった。ベンダの 0x29a6c は要求 +0xb0（本数）を副5 +0x824 に、
  +0xb8〜+0xc4（音声 4 本の表）を +0x828〜+0x834 にそのまま写し（模擬実行）、ファームは +0x828 を常に、
  +0x82c/+0x830/+0x834 は副5 +0x5c の bit12 が立つときだけ PID の照合に入れる（0x80186344〜0x80186384）。
  音声が 2 本以上の番組では、最大 4 本を要求に入れ、+0x5c の bit12 を立てる（`Options.multi_audio`・音声 1 本はベンダと同じ形）。
  Eテレ 1（2 音声の番組・同時受信の 2 本目）で 0x110・0x111 とも 1,360 本・平文・抜け 0、EPGStation と同じ ffmpeg で
  映像＋音声 2 本の出力。⚠️ 開いたときの PMT で決めるので、流している途中で番組が変わって音声が増えると拾えない
  （その回の ffmpeg は同じ形で失敗する）。PMT の変化を見て副5 を出し直すのは未実装。
- データ放送（0x138・0x140〜）と本放送の PCR は出力に無い。**データ放送には対応していない**（2026-11-18 に調べた:
  本放送のデータ放送は暗号化されていて、カードの中の 2 つの環はどちらも運ばない。[hardware.md](hardware.md) の「データ放送」）。

- **汲み出しの取りこぼし → 直した。** NHK 総合のライブ視聴で絵に帯状の崩れ。90 秒の取り込みで映像の 0.45%（3,271 本以上）が
  連続カウンタの飛びで抜けていた（受信の誤りの印は 0）。カードの環は約 0.2 秒ぶんしかなく、汲み出しが書き出し
  （橋 → Mirakurun → EPGStation の HLS 変換 `-re`）で待たされると追い越される。書き出しを別スレッドにして待ち行列を置いた
  （`Stream.pump`）後は、同じ条件の 90 秒で抜け 0・利用者の目視でも崩れが消えた。閉じるときに周回の間隔・書き出しの待ち・
  溜まりの最大をログに出す。
- **切り替え直後に F5 が要ることがある（未解決）。** チャンネルによる。選局し直して頭から取り込んだ番組単位の流れを
  EPGStation と同じ ffmpeg（`m2tsll`・`-analyzeduration 500000`）に読ませると、ch18〜27・40 の 11 局は毎回通り、
  ch13（J:COM テレビ）だけ 0 フレーム（選局し直しの無い途中からの流れでも同じ）。サーバー側で再現できたのは ch13 だけ。
- **本放送の PCR が出力に無い。** PCR の PID（ch27 は 0x01ff・ch25 は 0x0100）は汲み出す 2 つの環のどちらにも来ない
  （実験の記録と同じ）。ワンセグの PCR だけ残る。差し込んでも ffmpeg の結果は変わらなかったので F5 の原因ではないが、
  PCR を要る再生器のために直す余地がある。
- **頭のスクランブル。** B-CAS の起動し直しが 2 回かかった回は、準備完了から定常運転の終わり（3 秒）までが短く、
  汲み出しの頭の 1 秒ほど（ch27 で映像の 3%）が鍵の届く前のスクランブルのまま出た。同時受信とは別の、1 本だけのときと同じ仕組み。
  切り替え直後の F5 と関係するかは未確認。
- 定常運転を「復号が始まったら抜ける」（`Options.steady_until_dec`）は最初のバイトを約 1 秒早めるが、入れた後に F5 が要る回が
  増えたと報告があり（サーバー側では差を再現できず）、既定では切っている。起動し直しの見切りは 0.6 秒だと 1 回目で間に合わない回が
  増えたので 0.8 秒のまま。
