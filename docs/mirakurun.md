# Mirakurun で使う

Mirakurun にとってのチューナーは、「チャンネル番号を受け取り、その物理チャンネルの TS を標準出力へ出し続けるコマンド」です。
このドライバでは `stream` がそれにあたります。B-CAS の復号はカードの中で済んでいるので、Mirakurun の `decoder` は設定しません。

Mirakurun は公式の推奨どおり Docker（`chinachu/mirakurun`）で動かします。コンテナの中からはカードを扱えない（root 権限と
VFIO が必要な）ため、ホスト側の「橋」と、コンテナの中で動く小さなクライアントに役割を分けています。

```
Mirakurun（コンテナ）── spawn ── node /dth50/dth50-client.js <ch> <tuner>
                                     │ Unix ソケット（ホストの /run/dth50/tuner.sock）
ホスト: python3 -m dth50 bridge（root で常駐。カードを握り続け、複数のチューナーを同時に扱う）
```

| ファイル | 役割 |
|---|---|
| `dth50/bridge.py` | 橋。「チャンネル番号 [チューナー番号] + 改行」を受け取って受信を始め、TS をソケットへ流します。接続が切れたら、その受信だけを終えます。カードは一度開いたら握り続け、同じプロセスの中で複数のチューナーを同時に扱います（下の「同時受信」）。同じチューナーへの次の要求は、前の受信が終わるまで最大 30 秒待たせます。`--spawn` を付けると、以前の動き（要求ごとに `stream` を起動し、1 本ずつ受信）になります。 |
| `contrib/mirakurun/dth50-client.js` | コンテナの中で動くクライアント（Node の標準機能だけで動きます）。SIGTERM を受けるとすぐに接続を切ります。 |
| `contrib/mirakurun/docker-compose.override.yml` | 公式の `docker-compose.yml` に重ねて使う設定です（`/run/dth50` とクライアントを、コンテナの `/dth50` の下に渡します）。公式のファイルは書き換えません。 |
| `contrib/mirakurun/tuners.yml` | チューナーの設定例です。クライアントの 2 つ目の引数がチューナーの番号です。 |
| `contrib/systemd/dth50-bridge.service` | 橋の systemd ユニットです（リポジトリとベンダのデータの場所は `contrib/install.sh` が書き込みます）。 |

## 導入

ベンダのデータは、あらかじめ README の手順（`tools/setup_vendor.py`）で `/usr/local/share/dth50` に用意しておいてください。
別の場所に置いた場合は、`install.sh` に `--vendor DIR` を付けます。

```bash
# 1) Mirakurun を入れる（公式の手順）
sudo mkdir -p /opt/mirakurun && cd /opt/mirakurun
sudo wget https://raw.githubusercontent.com/Chinachu/Mirakurun/refs/heads/master/docker/docker-compose.yml
sudo docker compose pull
sudo docker compose run --rm -e SETUP=true mirakurun

# 2) 橋・クライアント・Mirakurun の設定を入れる
sudo bash contrib/install.sh install
journalctl -u dth50-bridge -n 3          # 「待ち受け /run/dth50/tuner.sock」と出ていれば起動しています

# 3) Mirakurun のコンテナを作り直し（override の設定を反映させるため）、チャンネルスキャンを行う（13〜62 を順に・数分かかります）
cd /opt/mirakurun && sudo docker compose up -d
curl -sS -X PUT "http://127.0.0.1:40772/api/config/channels/scan?type=GR"

# 4) 試しに 20 秒受信する
curl -sS --max-time 20 -o ch27.ts http://127.0.0.1:40772/api/channels/GR/27/stream
```

`localhost` は IPv6 の ::1 に向くことがあるので、127.0.0.1 を使ってください。
取り外すときは `sudo bash contrib/install.sh uninstall` を実行します。

## 同時受信

### チューナーの番号

橋は、動作を確認済みの機種のカードをすべて握り、カードをまたいだ通し番号をチューナーに振ります。カードを PCI アドレスの順に
並べ、カードごとのチューナーを続けて数えます。DT-H50/PCIEW と DT-H50/PCIE を 1 枚ずつなら 1〜3、PCIEW を 2 枚なら 1〜4 です
（どの番号がどのカードかは、橋の起動時のログ「チューナー N = …」に出ます）。`tuners.yml` には、カードの数だけチューナーを
並べてください。使うカードを限りたいときは、`--bdf` にカンマ区切りで PCI アドレスを並べます。

カードごとに、受信の席・ファームの区画・鍵の枠・命令の順番を別々に管理しています。1 枚目の受信（SECODE を出す受信）や、
カード全体を止める最後の命令（0x1a）も、カードごとに決まります。1 枚が応答しなくなっても、ほかのカードのチューナーは
引き続き使えます。

PCIEW と PCIE を 1 枚ずつ挿した環境で、ch27・ch25・ch22 の 3 番組を同時に受信し、3 本とも映像と音声が正しく復号できることを
確かめています。

### 1 枚のカードで 2 番組を受信する仕組み

DT-H50/PCIEW の 2 つのチューナーは、同時に使えます。カード内の復号の仕組み（SECODE）は 1 つしか載せられず、2 回送るとカードが
止まります。そのため 2 番組目は SECODE を送らず、復号器（副5）を正しくつないで開くだけにしています
（詳しくは [hardware.md](hardware.md) の「2 番組同時受信」）。

- 受信していないときに開くのが 1 番組目です（SECODE とカード全体の手順を出します）。もう 1 番組を受信している最中に開くときは、
  空いている席を使います。どちらを先に終えてもかまいません。最後に終える 1 本だけが、カード全体を止めます（0x1a）。
- カードへの命令は 1 つずつ送るので、もう一方を開いている数秒の間は、こちらの開始や終了が待たされます
  （受信中の番組は止まりません）。
- カードに渡す ES は、映像と音声だけです（2026 年 11 月 18 日から）。字幕や文字スーパー（種類 0x06）を渡していたころ、
  ch22（関東の TBS）を含む組み合わせで 2 番組同時の復号が崩れていたためです（[hardware.md](hardware.md) の
  「2 番組同時の復号が崩れる問題」）。平文の字幕は、表に渡さなくても出力に入ります。

### 異常への備え

- **復号が崩れた状態を見張ります。** 橋は開いているカードのファームの値 0x8021f4e8 を 1 秒ごとに読み（読むだけです）、
  値が増え続けたとき（1 秒に 30 以上、または合わせて 200 以上）に崩れたと判断して、時刻と直前の操作をログに残します。
  崩れたカードでは 2 番組目を開かず、その要求は空いている別のカードのチューナーを借りて受信し、終わったら返します。
  Mirakurun は要求を断られても別のチューナーへは移らず、同じチューナーを 0.15 秒おきに試し続けるため、断るだけでは
  視聴や録画が失敗してしまうからです。借りている間に、借りた先のチューナーへ要求が来た場合は、空くのを `--wait-busy` 秒
  待ってから断ります。
- **カードが応答しなくなった場合**（終了の命令が返らない、または起動時に前回の受信を閉じられない場合）は、そのカードへの要求を
  すぐに断ります（ログには 1 分に 1 回出します）。PCIe のリセットはチップまで届かないため、元に戻すにはマシンの電源を
  入れ直してください。
- 復号器（副5）が開けなかった場合は、ファームが確保したまま返さない区画と鍵の枠を戻し、1.5 秒待ってから 1 回だけやり直します。
- どの読み出し口（環）も 5 秒進まなければ、その受信を終えて Mirakurun に知らせます。
- 橋を `--spawn` で動かす場合は 1 本ずつしか受信できないので、`tuners.yml` の 2 つ目以降を `isDisabled: true` にしてください。

## 出力される TS

- 映像・音声・字幕・番組表（EIT）などの PSI/SI・PCR・ワンセグが入ります。
- **データ放送は入りません**（[hardware.md](hardware.md) の「データ放送」）。データ放送は暗号化されていて、カードはこれを
  復号しません。暗号化されたままのパケットはカードから届きますが、橋がまとめて捨てます（EPGStation の「スクランブル」の数が
  増えないようにするためです。捨てた本数と PID は、受信を終えるときにログに出ます。1 本あたり約 2 Mbps です）。
- 音声が 2 本以上ある番組では、最大 4 本までを復号して出力します。ただし、受信を始めたときの PMT で決めるので、受信の途中で
  番組が替わって音声が増えた場合は拾えません（PMT の変化に合わせて復号器を開き直す処理は、まだありません）。

## 動作確認の記録

### 2026 年 11 月 5 日（開発環境・Mirakurun 4.2.1）

- 橋は起動時に自動で立ち上がり、Mirakurun の番組表の取得（ch13・ch18 など）がそのまま流れました（番組表 8,880 件）。
- `/api/channels/GR/27/stream` を 20 秒受信すると、Mirakurun は番組表の取得を止めて ch27 に切り替えました。
  140,708 パケットで、188 バイトの区切りのずれは 0、映像 0x0100 と音声 0x0110 はすべて平文、Mirakurun のエラーの数もすべて 0 でした。
- EPGStation 2.10.0（Docker で動かし、Mirakurun に 127.0.0.1:40772 でつなぐ）で時刻指定の予約を 2 分録り、199 MB の .m2ts が
  できました。映像と音声はすべて平文でした。
- 非公開の実験用リポジトリにあった橋（`tools/dth50-bridge.py` → `dth50-mirakurun.sh` → `run-ch27-vendor.sh` → `s4-boot`）から
  置き換えました。クライアントとソケットのやり取りは同じ（チャンネル番号だけの行も受け付けます）なので、古いクライアントのままでも
  動きます。
- 同時受信（8 時 15 分ごろから・Mirakurun に 2 チューナーを登録）: ch27・ch25・ch18 を重ねて受信しました。ch25 はすべて平文で
  抜けも無く、ch25 の受信中に空いたチューナーで開いた ch18 もすべて平文でした。番組表の取得でも 2 チューナーを同時に使います。
  ch27 の頭の 1 秒ほどにはスクランブルが残りました（下の「受信を始めた直後のスクランブル」）。

### 2026 年 11 月 18 日

- PCIEW と PCIE を 1 枚ずつ挿し、Mirakurun に 3 チューナーを登録して使っています。
- PCIEW の復号が崩れた状態（電源を入れ直す前）でも、ch27 は PCIEW で、チューナー 2 への ch25 の要求は PCIE を借りて、
  同時に受信できました。3 本目の要求は断られました。

## 既知の問題と、これまでに直したもの

- **2 本目の音声が無く、ライブ視聴が映らない → 直しました（2026 年 11 月 6 日）。** NHK 総合の番組の PMT に 2 本目の音声 0x111 が
  載ったとき、出力に 0x111 が 1 本も無く、EPGStation の ffmpeg（`-map 0`）が中身の無い音声で変換を始められずに失敗していました
  （`Error initializing filters!`）。原因は、0x31 の要求に音声を 1 本しか入れていなかったことです。ベンダのドライバ（0x29a6c）は、
  要求の +0xb0（音声の本数）を副5 の +0x824 に、+0xb8〜+0xc4（音声 4 本の表）を +0x828〜+0x834 にそのまま写します。ファームは
  +0x828 を常に、+0x82c・+0x830・+0x834 は副5 の +0x5c の bit12 が立っているときだけ、PID の照合に使います（0x80186344〜0x80186384）。
  音声が 2 本以上ある番組では、最大 4 本を要求に入れ、+0x5c の bit12 を立てるようにしました（`Options.multi_audio`。音声が 1 本の
  ときはベンダと同じ形です）。Eテレ 1 の 2 音声の番組で、0x110・0x111 ともすべて平文・抜け 0 で、EPGStation と同じ ffmpeg で
  映像と 2 本の音声を出力できました。
- **読み出しの取りこぼし → 直しました。** NHK 総合のライブ視聴で、絵に帯状の崩れが出ていました。90 秒の取り込みで映像の 0.45%
  （3,271 本以上）が、連続カウンタの飛びとして抜けていました（受信エラーの印は 0）。カードの中の環は約 0.2 秒分しかなく、
  読み出しが書き出し（橋 → Mirakurun → EPGStation の HLS 変換 `-re`）に待たされると追い越されます。書き出しを別のスレッドに分け、
  待ち行列を置いた（`Stream.pump`）ところ、同じ条件の 90 秒で抜けは 0 になり、目視でも崩れが消えました。受信を終えるときに、
  周回の間隔・書き出しの待ち・溜まった量の最大をログに出します。
- **本放送の PCR → 出力に入るようになりました（2026 年 11 月 18 日）。** 以前は PCR の PID（ch27 なら 0x01ff）が、どちらの環にも
  来ていませんでした。カードに渡す ES を映像と音声だけにしてから、平文で届くようになりました（ch27 で 15 秒に 149 本）。
- **チャンネルを切り替えた直後に、再読み込み（F5）が必要なことがあります（未解決）。** チャンネルによって違います。選局し直して
  頭から取り込んだ番組単位の流れを、EPGStation と同じ ffmpeg（`m2tsll`・`-analyzeduration 500000`）に読ませると、
  ch18〜27・40 の 11 局は毎回通りますが、ch13（J:COM テレビ）だけは 0 フレームになります（選局し直さない途中からの流れでも
  同じです）。サーバー側で再現できたのは ch13 だけです。
- **受信を始めた直後のスクランブル。** B-CAS カードの起動し直しが 2 回かかった回は、準備完了から定常運転の終わり（3 秒）までが
  短く、出力の頭の 1 秒ほど（ch27 で映像の 3%）が、鍵が届く前のスクランブルのまま出ます。1 番組だけの受信でも同じ仕組みで
  起きます。チャンネル切り替え直後の F5 と関係があるかは確かめていません。
- 定常運転を「復号が始まったら抜ける」設定（`Options.steady_until_dec`）は、最初のデータを約 1 秒早めますが、有効にした後に
  F5 が必要な回が増えたという報告があり（サーバー側では差を再現できていません）、既定では無効にしています。B-CAS カードの
  起動し直しを待つ時間は、0.6 秒にすると 1 回目で間に合わない回が増えたので、0.8 秒のままにしています。
