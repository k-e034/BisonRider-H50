# 対応機種とハードウェア

## 機種の見分け方

どの機種もチップは ViXS XCode 2100（PCI `1745:2100`）で、VEN/DEV では区別できない。
機種は PCI の **SUBSYS** で決まる（ベンダのドライバの `BufFullSeg.inf`）。

| 機種 | SUBSYS | チューナー | 実機での確認 |
|---|---|---|---|
| DT-H50/PCIEW | `1154:0548` | 2 | 2 つとも受信・カード内復号・2 本同時・Mirakurun まで確認 |
| DT-H50/PCIE | `1154:0540` | 1 | 未確認 |
| DT-H50/PCIE | `1154:0542` | 1 | 受信・カード内復号・橋で PCIEW と 3 本同時まで確認（2026-11-18） |

挿さっているカードは `python3 -m dth50.models` で分かる（`/sys/bus/pci` を読むだけ）。

`BufFullSeg.inf` は同じ系列の 16 機種を列挙している（DT-H50/PCI・PCI-B・LowProfile など）。
このドライバが対象にするのは上の 2 機種だけ。

## 機種ごとの構成（ベンダの機種表）

ベンダの `BufFsLiveFilter.ax` の `.rdata` に、機種名を先頭に持つ 0x14c バイトの構造体が 25 機種ぶん並んでいる。
DT-H50/PCIEW と DT-H50/PCIE（2 件）の欄（16 ビット幅・0 の欄は省略）:

| 欄 | PCIEW | PCIE（1 件目） | PCIE（2 件目） | 読み |
|---|---|---|---|---|
| +0x104・+0x106 | 1・1 | 1・1 | 1・1 | 世代（H50・PCIE 系 = 1） |
| +0x108・+0x10a | 1・1 | 1・1 | 1・1 | バス（PCI / PCIE = 1） |
| +0x10c | 2 | 1 | 0 | 基板の改訂 |
| +0x10e | 2 | 2 | 2 | |
| +0x110 | 1 | 0 | 0 | PCIEW だけ 1 |
| +0x116 | 2 | 0 | 0 | 2 チューナー機だけ |
| +0x118 | 0x10 | 0x1 | 0x1 | GPIO のビット（PCIEW はビット 4） |
| +0x11c | 1 | 1 | 1 | |
| +0x120 | **2** | **1** | **1** | **チューナーの数** |
| +0x12a | 1 | 1 | 1 | |
| +0x12e | 1 | 0 | 0 | 2 チューナー機だけ |
| +0x138 | 0x10d | 0x10f | 0x110 | 機種コード |
| +0x13e | 1 | 1 | 1 | |
| +0x140 | 0xb7 | 0xa3 | 0xbe | 未解明 |

- **PCIEW の「W」は 2 チューナー**（+0x120 = 2 の機種は DT-H70/U2W・DT-H70/PCIEW・Dual・DT-H50/PCIEW の 4 つだけ）。
  2 つのチューナーは I2C バスを共有し、**GPIO 4 でつなぎ先を切り替える**（ベンダのフィルタは
  `Global\Mutex_BuffaloFsGPIOWithI2c` を取ってから切り替える）。
- PCIE は 1 チューナーで、この切り替えが無い。
- PCIE の 2 件が SUBSYS `0540` / `0542` のどちらにあたるかは、実機で未確認。

## DT-H50/PCIE（2026-11-17・開発機に PCIEW と 2 枚挿し・分配器で同じアンテナ）

- **基板 ID**（BAR2+0x478 & 0xf3ffffff）の下位が PCIEW の 0xb6 に対して **0xa3**。ベンダのドライバはこれを毎回の MMIO の前に
  「カードが居るか」の確かめに読むだけなので、初期化列（PCIEW で採ったもの）は基板 ID の世代の部分
  （& 0xf3ff0000）だけを比べれば、残りはそのまま通る（初期化列・ファームの転送・転送後の手順とも）。
  機種表で +0x140 = 0xa3 なのは PCIE の 1 件目（機種コード 0x10f）。
- **チューナー**: ベンダのドライバ（`BufFullSeg.sys` の XP 版・チューナー初期化 0x3ee24 の表）は基板 ID a2/a3 で
  「This tuner board has SONY's tuner(SMT-MJ100).」を出し、I2C は **0x20 / 0xC0 だけ**を初期化する（0x30 は無い・
  `20 ← 1d..1f/1c = aa`・`20 ← 04 20 / 03 70`・`c0 ← 95 fb fe / 09 41 fe`）。PCIEW の 2 つ目（組 2・`TunerMJ110`）の列が
  そのまま通じ、ch27 で CNR 0x0026xx〜0x002cxx（分配器の後・PCIEW と同じくらい）でロックした。
- **TS は入力 0**（副1・副5 の +0x08 = 0）。入力 1 では 1 パケットも来ない。
- 機種表（`models.tuner_map`）: PCIE のチューナー 1 = 組 2・入力 0。PCIEW は 1 = 組 1・入力 0、2 = 組 2・入力 1。
- 実機: ch27 20 秒・ch25 30 秒とも、映像・音声が頭（B-CAS の起動し直しの分）を除いて全部平文・抜け 0・閉じる命令は全部返る。
  EPGStation と同じ ffmpeg で絵が出た。
- 橋（Mirakurun）からも使える（2026-11-18）: 橋はカードごとに握り、PCIEW と合わせて 3 チューナー（docs/mirakurun.md）。
- 残り: 1154:0540（もう 1 つの改訂）は未確認。

## DT-H50/PCIEW の 2 つ目のチューナー

**2026-11-04 実機（開発機）でロックした**: ch27 CNR 0x00cd〜0x00e2xx・ch13 CNR 0x0080〜0x009bxx。
`sudo python3 -m dth50 tuner-probe --tuner 2 -c 27`。I2C 列は `tools/extract_mj110.py` で作る（下）。

### 列の出どころ（tools/extract_mj110.py）

ベンダのフィルタ `BufFsLiveFilter.ax`（PCIEW 用ドライバ 1.63・sha256 `541e302d…`）の MJ110 を扱うクラス（仮想関数表 0x1003463c）を
unicorn で動かし、I2C の書き込みと Sleep を記録する。

| 仮想関数 | 番地 | 働き |
|---|---|---|
| +0x48 | 0x1000f710 | 番号の設定。0 → チューナー 0xC0・復調器 0x20（MJ110）、1 → 0xC6・0x30（1 つ目） |
| +0x14 | 0x1000d8a0 | 初期化: `c0 ← 09 b1`・10 ms・表 0x100344d8（印 FA = チューナー / FB = 復調器・118 件）・+0x38（`20 ← 52 20`）・周波数 -1 で一度選局 |
| +0x2c | 0x1000e070 | 選局 (周波数 Hz, 強制): `20 ← 1e a8 / 1f a8` → チューナーの分周値など 18 件 → 30 ms → `c0 ← 88 fe / 09 f3` → `20 ← 01 40 / 76 87` → 30 ms → `20 ← 1e 80 / 1f 08` |
| +0x54 | 0x1000f230 | I2C 書き込み (クロック 400 kHz, 宛先, レジスタ, バッファ, 長さ)。チューナー宛ては後ろに 0xFE を足す |
| +0x1c〜+0x28 | 0x1000dfa0 など | 状態の読み（0x80・0xB0・CNR 0x8B〜・0x81・0x82）。ロックの判定は 1 つ目と同じ（0x80 & 0x28 = 0 かつ 0xB0 下位 ≥ 8） |

- 分周値 N は reg 0x0f（N >> 10）・0x10（N >> 2）・0x11（(N << 6) | 0x20）に分けて書く。1 単位 ≒ 250 Hz。
- ベンダは周波数を kHz に丸めて渡す（ch18 = 503,143,000 Hz）。丸めないと reg 0x11 の上 2 ビットが変わる。
- エミュレータの列は XP の採取（「1 つ目で視聴・2 つ目で録画」）と全件一致した（初期化の中の選局・ch18 の選局とも）。
- ⚠️ それまでロックしなかったのは、XP の採取の道具が同じ中身の呼び出しを 2 回目から記録しておらず、選局の末尾
  （`c0 ← 09 f3 / 88 fe / 09 f3`・`20 ← 01 40 / 76 87`・`20 ← 1e 80 / 1f 08`）が列から落ちていたため。
  末尾の `1e 80 / 1f 08` を入れた列で 1 回目の読みからロックした。

**TS も取れた**（2026-11-04・`stream --tuner 2 -c 27`・warm・2 回とも）: dec 13.9〜14.1 Mbps、映像 0x100・音声 0x110 が平文（PES の開始あり）。
変えたのは選局（TunerMJ110）と、0x08 副1 の引数 +0x08（カードへの入力の番号）= 1 だけ。

- ドライバは 0x2E の要求 +0x84 を 0x08 副1 の引数 +0x08 へそのまま写す（`BufFullSeg.sys` 0x288b5: `0x39c64(文脈, &要求+0x84, &引数+0x08, 4)`）。
  XP の採取で 0x2E の 1 つ目と 2 つ目の違いはこの欄だけ（0 / 1）。
- 0x31 の要求で違う +0x8C・+0xB4（0 / 1）は、ドライバの中で 0x2E の流れのオブジェクトを引く番号（0x29e95・0x29f22 で
  文脈 +0x174 / +0x344 に入れて参照を数える）。カードへの引数には写らないので、移植では使わない。

### 2 つを同時に使う（2026-11-05・橋に組み込み済み）

- 1 つ目の初期化列（`tuner-seq.txt`）は 2 つ目を休ませる書き込み（`c0 ← 95 fb / 09 41`・`20 ← 03 70` など）を含む。
  もう 1 本が流れている最中に開く回はこれを飛ばす（`Options.tuner_others`）。2 つ目の列は 1 つ目に触らない（実験 11 で 1 本目が止まらない）。
- 席（`stream.SEATS`）: 席 0 = 副1 枠 5・副5 枠 12・IOVA 0x20000000（IOVA 0 の頁も）／席 1 = 副1 枠 7・副5 枠 11・IOVA 0x30000000・
  副5 の `+0x010` = 1・`+0xacc` = 7（XP のベンダの 2 本目と同じ）。流れが無いときに開く回は席 0 で SECODE とカード全体の手順を出す。
  もう 1 本が流れている最中に開く回は空いている席で、SECODE も欄の写しもせず、副5 を正しくつないで開くだけ（`stream.seat_options`）。
  ⚠️ 2026-11-18 まで「SECODE の欄 52 語を流れている方の副5 の文脈から写す」としていたが誤り（下の「2 本目の復号が壊れていた」）。
- 閉じる: 自分の文脈だけを閉じ（0x0d → 0x09 副5 → 0x09 副1）、最後の 1 本だけが 0x1a を出す（`Stream.close(last=…)`）。
- **席のバッファの IOMMU の割り当ては外さない**（常駐の橋が持ち続けて使い回す）。1 本目の 0x1b で登録した制御ブロックと
  IOVA 0 の頁はカード全体のもの（実験 12 で外してカードが止まった。当時は欄を写していて、写した `+0x28a4`・`+0x9168` が
  1 本目の 0x15 の選択器の頁 `0x20510000` も指していた）。

### 2 本目の復号が壊れていた（2026-11-17〜18）

- 利用者から「PCIEW で 2〜3 秒流すと固まる」。視聴中の 2 本目の映像を調べると、**暗号の印（scrambling bits）はすべて 0 なのに
  PES の始まり（00 00 01）が正しくない**（14〜62%）。カードが印だけを消して中身を正しく復号していなかった。それまでの確かめ
  （実験 11・2026-11-06・試験 5 回）は印と連続カウンタしか見ておらず、これを見逃していた。
- `tools/dual_pes.py` で 1 秒ごとに PES の始まりを見ると、**欄を写した 2 本目が流れ始めて 4〜20 秒後（最初の鍵の切り替わり）に、
  1 本目も含めて 2 本とも 0% になり戻らない**。同じ局でも違う局でも同じ。11-06 の版（f1cf2da）でも同じだった。
- 2 本目に自分で SECODE を出させると、1 本目が止まりカードも止まる（実験 1〜10 と同じ・完了の待ち方を直した後でも）。
- XP の採取（ref/xp/vt）: ベンダの 0x0b 種類 0x200000（1 本目の文脈へ TS 1 パケット）は 1 本だけの視聴でも出ていて、2 本目の
  鍵とは関係しない（中身は PID 0x3f0・ワンセグ 0x581 のパケット）。
- **正しくつないで（+0x028・+0x010・+0xacc・+0x08）、SECODE も写しもせずに開く**（これまで試していなかった組み合わせ。実験 1〜9 は
  つなぎ違い、10 は SECODE、11 は写し）と、2 本とも 100% 正しく復号した。5 分の試し（1 本目を先に閉じる・SECODE を出した流れが
  無くなった後に 3 本目を開く）も全部 100%。写す欄に鍵の置き場（枠+0x147c〜）が入っていて、2 本の鍵の状態が
  ぶつかっていたと見ている。
- 直した後の 20 分の試験（2026-11-18 01:20〜・65 回・3.84 GB）: PES の始まり 117,976/117,976（100%）・開けない回・抜け・ずれ 0、
  区画と鍵の枠は冷えた状態の値に戻った。

### 2 本同時で起きた致命的な失敗と直し方（2026-11-17）

2026-11-11 に録画中の 2 本目でカードが止まり（録画は 8 分 54 秒で切れた）、11-13 にも同じ形で止まった。どちらもマシンの電源を
入れ直すまで戻らなかった（PCIe のリセットはチップに届かない）。原因は 4 つ重なっていた。

1. **完了の待ち方が 1 本向けだった。** 命令の完了とデータのイベントは同じレジスタ（0x30e0）で知らされる。`open()` の
   0x19・0x0b・副1 と定常運転の 0x0b は「次のイベント」を待っていて、もう 1 本が流れているとそのデータのイベントで素通りし、
   命令が完了を待たずに続けて出ていた（0x0b はどちらの流れも枠 1）。`await_cmd` は「イベント 12 回」で諦めていたので
   数 ms で諦め、取り残された完了が後の別の待ちに拾われた（11-13: 副1 の待ちが 0x0b の完了を、副5 の待ちが副1 の完了を拾った）。
   → 完了は命令と枠で合わせて秒数まで待つ。命令を出す前に取り残しの完了を片付けてログに出す（`Card.flush_events`）。
2. **閉じる宛先を確かめていなかった。** 副5 が文脈を返さなかった回に、引数域 +0x18 に残ったホストの IOVA（`ctl8b` =
   0x30548000）を文脈と思って 0x09 を出し、カードが止まった（11-11）。→ 0x09 は文脈の番地（0xa02xxxxx / 0x802xxxxx）にだけ出す
   （`card.is_ctx`）。
3. **副5 の失敗がファームの資源を取り残す。** 副5 の処理（`0x801860a8`）は区画の表（`[gp-0x6b98]`・13 項目・副5 1 本で 2）と
   鍵の枠の表 A・B（`0x802023cc` / `0x802023ec`・31 個ずつ・1 本で A 8〜10 / B 4）を確保してから検査に進み、失敗すると
   確保した分を返さずに終わる。失敗が重なると表が尽き（区画 11/13・表 A 30/31 まで行った）、以後どの 2 本目も開けない。
   冷えた状態は 区画 1・A 6（0〜5）・B 1（0）。→ 副5 を出す前に表を控え、文脈が返らなければ増えた分だけ印を戻す。
4. **ファームの PID の表（`0x8020a440`・30 段・`0x8019dcf0`）が 2 本で足りない。** 副5 が失敗した理由（`[gp-0x7544]`）は
   0xf（PCR の PID を登録できない）。ES の多い局どうし（14 本＋13 本）で起きる。ES の大半はデータ放送のカルーセル（0x0d）で、
   カードはそれをもともと出力しない。→ カードに渡す ES を映像・音声・0x06（字幕・文字スーパー）だけにする（`open31.ES_KEEP_TYPES`）。

ほかに: 汲み出しの最初の読みが環のパケットの途中から始まり、回の全部が 188 の区切りでずれることがあった（→ 0x47 が 188 おきに
3 つ並ぶ位置で合わせ、ずれたら合わせ直す）。データが止まっても気づかず 10 分空回りした（→ どの環も 5 秒進まなければ終える）。
カードが応答しなくなったら、橋は起動し直しを繰り返さず（11-11 は 189 回）要求をすぐ断る。

試し方: `tools/stress_bridge.py`（2 チューナーで 5〜90 秒の回・0〜0.3 秒の開き直し・同時に開く回を混ぜる）。直した後の 20 分
（2026-11-17 13:51〜・68 回・3.97 GB）は開けない回・暗号のまま・抜け・区切りのずれがすべて 0、終わった後の区画・鍵の枠は
冷えた状態の値に戻った。橋のログは開く・閉じるのたびに区画・表 1/2 の文脈・鍵の枠を出す（読むだけ）。

### 調べた経緯（2026-11-04）

**基板に見えるチップ**（2026-11-04・目視）: Sony SMT-MJ110（W8L11AB）・Sony SMT-MJ100（W9F17AB）・Toshiba TC90507XBG（0832HAL）。
TC90507 の隣で配線がつながっているのは SMT-MJ100（W9F17AB）（目視）。これで 2 系統の中身が決まる:

| 系統 | I2C | 中身 |
|---|---|---|
| 1 つ目（今まで使ってきた側） | 復調器 0x30・チューナー 0xC6（ゲート 0xFE 越し） | TC90507 ＋ SMT-MJ100（チューナーだけのモジュール） |
| 2 つ目 | 復調器 0x20・チューナー 0xC0（主バスに並ぶ） | SMT-MJ110（復調器を内蔵したモジュール） |

- 単体の復調器は TC90507 の 1 つだけなので、0x20 は SMT-MJ110 の中にある。状態の読みの番地が 1 つ目と同じなので、中身も Toshiba 系の復調器と見ている（未確認）。
- ベンダのドライバのデバッグ文字列が SMT-MJ110 と "at 2nd tuner" を結んでいる（0x3ee77）のとも合う。**ドライバのこの辺りが 2 つ目の初期化そのもの**なので、
  0x20・0xC0 の初期化と周波数の計算はここを読むのが近道。
- モジュールの型番が違うので、チューナーのレジスタも周波数の式も 1 つ目からは借りられない。
- **RF の経路: アンテナ端子から直に入るのは SMT-MJ110（2 つ目）**（目視）。1 つ目（MJ100）は MJ110 を通った RF を受けていると見ている
  （MJ110 のループスルー出力か分配。未確認）。つまり 2 つ目の CNR 0 は RF が届いていないせいではなく、MJ110 への書き方の問題。
  逆に、**1 つ目を使うときも MJ110 の状態が効く**かもしれない: ベンダの 1 つ目の選局列が 0x20・0xC0 にも書いている
  （c0 ← 95 fb / 09 41 など。今まで「2 つ目の休止」と読んでいたもの）のは、MJ110 を休ませつつ RF を通す設定の可能性がある。

ベンダのフィルタ・ドライバの静的解析と、XP で「1 つ目で視聴しながら 2 つ目で録画」した間の DeviceIoControl の採取
（実験用リポジトリ（非公開） `ref/iohook-3`）から:

- **GPIO では切り替えない。** フィルタの I2C の入口（`BufFsLiveFilter.ax` 0x1001f4f0）が GPIO 4（＝ BAR2+0x1088 の bit2。
  ドライバのコマンド 0x22 操作 8）を叩くのは機種の種別が 4 / 8（Dual・U2W）のときだけ。PCIEW は 0x10。採取にも 0x22 は 0 件。
- **2 系統は別の I2C アドレスで、2 つ目は別のチップ構成。**
  | | 復調器 | チューナー | 書き方 |
